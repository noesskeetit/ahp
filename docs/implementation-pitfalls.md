# Подводные камни реализации PDF rev3.2

Этот файл фиксирует ограничения продукта и принятые технические решения. Он не расширяет требования PDF. Базовый аудит выполнен на 7c810ec2; новые пункты ниже возникают при реализации и требуют проверки на объединённой версии.

## 1. Доступ AS только через API меняет границу доверия

Прямой вызов внутреннего budget ledger выполнялся доверенным кодом runner. Публикация тех же методов как HTTP API не делает поля `bound`, `reached_child` и `steps_consumed` доверенными. Произвольный агент не должен увеличивать лимит или освобождать резерв неподтверждённым отчётом.

Решение: owner проверяет текущую task authority и право конкретного workload на привилегированную операцию; лимиты и окончательный расчёт должны опираться на разрешённый источник. Регрессии: завышенный bound, поддельный нулевой расход, чужой task, потерянный ACK и UNKNOWN. Наличие mTLS само по себе не даёт всем агентам системных полномочий.

Для общего процесса `role=all` разрешён узкий in-process State owner API, внедрённый composition root вместе с действующей owner authorization. Model handler не получает State pool и не конструирует свой State store. Это использует разрешённое PDF укрупнение deployables; внешний AS по-прежнему использует только HTTP API. Отдельный Model process без такого authority adapter не должен включать эти привилегированные операции. Цена решения: для полностью раздельного размещения понадобится поддержанный межсервисный authority adapter, а не пересылка AS task token под чужим mTLS-сертификатом.

## 2. Большой checkpoint ограничен дважды

У State есть предел части и предел всего HTTP-запроса. JSON/base64 и совокупность частей увеличивают размер. Переносить только один явно большой blob недостаточно: SDK должен контролировать сериализованный запрос целиком и сохранять metadata/pending writes.

Решение: automatic Artifact spill с ограниченным дескриптором, immutable версией, digest и размером; чтение повторно авторизуется. Существующий лимит State сохраняется. Маркер ссылки обязан отличаться от пользовательских данных, чтобы обычный JSON случайно не стал командой загрузить другой объект.

## 3. Готовность байтов и готовность текста различны

PNG, ZIP, сериализованный checkpoint и произвольный tool output могут быть корректным Artifact без поддерживаемого текстового parser. Отсутствие extractor не означает вредоносность файла. При этом повреждённый документ поддерживаемого формата или отказ sandbox нельзя объявлять успешно разобранным.

Решение: отдельные content/extraction/search/quarantine статусы, явная поддержка MIME и fail-closed обработка требуемого разбора. Cache tenant+SHA не даёт права читать файл: на каждом доступе заново проверяются текущие права и метки источника.

У существующего Go Artifacts transport пока нет признака `OutcomeUnknown`: потеря HTTP-ответа, ошибка чтения или декодирования могут вернуться как `INVALID_ARGUMENT` либо context error. Такой ответ после отправки mutation не доказывает отсутствие записи. Клиент не повторяет вызов автоматически; для BeginUpload/Seal/Copy нужно сохранять исходный operation key/ID, для Process — проверять Readiness того же ID. Пять добавленных Go read/derive методов сохраняют этот transport. Явная классификация неопределённого результата на уровне Go transport остаётся отдельным пробелом паритета с Python.

## 4. Timeout не является изоляцией parser

Ограничение времени не запрещает чтение файлов хоста или сеть. Нужны реальный процессный sandbox, очищенное окружение, ограничения памяти/CPU/output и проверка запрещённых системных вызовов. Если выбранный runtime не поддерживает изоляцию, он должен честно отказать в разборе, а не объявить её реализованной. Приёмка Linux parser отдельно от macOS source build.

`PR_SET_NO_NEW_PRIVS` меняет состояние вызывающего OS-потока. Между этим вызовом и установкой seccomp Go может перенести goroutine на другой поток, где флаг ещё равен нулю; тогда ядро возвращает `EACCES`, а корректный документ получает `parser_refused`. Установка sandbox привязывается через `runtime.LockOSThread` до завершения TSYNC. Набор разрешённых syscall, resource limits и fail-closed поведение сохраняются. Регрессия принудительно занимает прежний поток между вызовами и проверяет реальный `no_new_privs`, thread ID и вывод parser; обычные отрицательные проверки сети, файлов, exec, памяти и CPU остаются отдельными. Основание: [Linux seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html), [Go LockOSThread](https://pkg.go.dev/runtime#LockOSThread).

## 5. Общий чат нельзя реализовать снятием subject filter

**Статус после решения пользователя 03.11.2026:** историческое ограничение для отложенного Agent Space. Dot личный; общий чат не блокирует текущую приёмку AHP. Описанная ниже опасность ослабления scope остаётся актуальной для платформенных API.

PDF разделяет владельца общего чата (проект) и автора каждого хода (сотрудник). Текущий State хранит личные threads по tenant/deployment/subject. Без явного контракта проекта удаление фильтра subject откроет чужие личные состояния.

Предстоящая реализация должна отдельно сохранить owner/audience, автора хода, личные credentials и свежую проверку членства. Возможные внутренние схемы хранения не являются разрешением заменять сотрудника синтетическим субъектом без проверки downstream token/lease/checkpoint контрактов. Проверка обязательна для выхода участника и старых SSE/download ссылок.

## 6. Внешний IAM/KMS требует настоящего контракта и среды

OIDC/JWKS и RFC8693 имеют отдельные адаптеры. Это не подтверждает интеграцию с конкретным корпоративным IdP, IAM Evaluate или tenant KMS. Публичная выдача access token не тождественна ресурсному Evaluate.

Нельзя придумывать production URL/схему Evaluate или объявлять тестовый HTTP provider настоящим IAM. До внешней приёмки фиксируются endpoint/issuer/audience, правила ресурсов, отзыв и ключи через secret store. Для KMS требуется конкретная конфигурация хранения и ключей. Недоступность внешней проверки не мешает реализовать owner interfaces и закрытое по умолчанию подключение.

## 7. Scope успешной проверки

Source commit, конкретная среда и поведение фиксируются отдельно. Успешный build, fixture или тест одного блока не подтверждают deployment и весь PDF. Same-host failover не доказывает отказ независимого storage node. Числа расчётной модели нагрузки не являются достигнутой ёмкостью.


## 8. Ссылка из checkpoint должна пережить сборку мусора

Большие значения теперь сохраняются в Artifacts, а State хранит ссылку. Сканер ссылок защищает уже записанный checkpoint, но первоначального сканирования недостаточно: State может записать ссылку после сканирования и до удаления файла.

Согласованный контракт реализации: перед фиксацией ссылки State получает у Artifacts владельца устойчивое временное удержание конкретной версии. Удержание создаётся под теми же блокировками, что использует GC. После подтверждённого завершения транзакции State удержание снимается; неизвестный исход сохраняет его до сверки. Перед удалением GC повторно спрашивает владельцев ссылок под блокировкой объекта. State не читает таблицы Artifacts напрямую.

Для сверки State держит транзакционную advisory-блокировку уникальной операции до commit/rollback. Успешная проверка освобождения этой блокировки через State owner API доказывает завершение исходной транзакции. ID операции не переиспользуется. Один лишь TTL удержания или временная блокировка на соединении Artifacts этого не гарантируют при обрыве связи. Эта реализация принята по независимой проверке checkpoint-gc и включена в объединённый кандидат cd6e6b6c; его полный Linux-контроль прошёл. Это проверка данного механизма на реальных владельцах, а не доказательство HA между независимыми storage nodes.

## 9. Формат ссылки не определяется по похожим пользовательским байтам

Произвольный старый blob может начинаться с любого magic prefix, а JSON пользователя — содержать любое обычное имя поля. Поэтому новый формат имеет отдельный сохранённый признак encoding у части, metadata и pending write. Пустой encoding всегда означает старые непрозрачные данные; SDK не пытается распознать в них ссылку.

В дескриптор входят неизменяемые свойства версии. Текущие метки доступа проверяются при чтении, но не меняют fingerprint повторной записи checkpoint. Go JSON и PostgreSQL JSONB принимают разные множества строк; форматный валидатор и сканер должны согласованно обрабатывать недопустимые Unicode escape, чтобы одна запись не останавливала очистку остальных данных. Исправление этой границы проверяется отдельно от гонки GC.

## 10. Готовность AHP, личного Dot и адаптера фреймворка — разные результаты

По прямому решению пользователя 03.11.2026 Dot личный, текущий фокус — AHP, а SDK требуются и для Python, и для Go. [Граница приёмки](decisions/2026-11-03-ahp-first-personal-dot.md) изменена явно: общие чаты/приглашения и остальные новые продуктовые функции Agent Space отложены. Это не основание объявлять весь исходный PDF выполненным, удалять готовый AS код или ослаблять права AHP.

Python SDK должен быть общим клиентом платформы; LangGraph saver — один из его адаптеров. Go SDK закрывает те же платформенные возможности и поведение ошибок/повторов. Наличие одного адаптера не доказывает поддержку других фреймворков: при исследовании каждого фиксировать собственную модель session/state/checkpoint, необходимый adapter, ограничения и оценку доработки. Не обещать универсальный checkpointer без проверки.

В памяти коллеги личные и личные проектные банки не становятся общими от добавления участника. Это согласуется с личным Dot, но не означает, что AHP стал однопользовательским. Проверки чужого tenant/subject, актуальных проектных прав, отзыва и удаления продолжают действовать независимо от UI.

## 11. Native Memory использует собственные вызовы моделей

Интегрированный Hindsight действительно извлекает и возвращает факты через Memory owner API. Однако его extraction и rerank пока не списываются из task/tree budgets AHP Model Gateway. Успешный retain/recall не означает, что общий бюджет задачи охватывает эти расходы. До бюджетной приёмки требуется определить владельца списания и ограничений, включая асинхронную обработку после завершения исходного run. Варианты — поддержанный маршрут inference через Model Gateway либо явно отдельная согласованная квота Memory; выбор меняет продуктовый контракт.

Автоматический State → outbox → Memory срабатывает для поддержанного payload типа turn и его проверяемых State evidence references. Произвольный сторонний harness не получает автоматическое извлечение из неизвестного формата checkpoint. Он должен либо использовать поддержанный turn-контракт, либо вызывать публичный Memory SDK с разрешёнными ссылками на источники. Private-project и личные банки сохраняют ограничения владельца.

## 12. Журнал Tool Gateway не равен результату инструмента

Текущий Tools Get намеренно отдаёт журнал операции без raw MCP result. Сохранённых байтов Result недостаточно для безопасной публикации: результат должен сохранять исходные task/context и метки доступа. Иначе повторное чтение из другого context того же пользователя может пропустить метку private OAuth источника, которую сейчас добавляет только dispatch.

Поэтому получение raw result остаётся открытым владельческим контрактом: атомарные completion и provenance, свежие права на operation и connection, добавление исходных меток до выдачи текста, отказ для legacy записей без provenance, а для большого результата — ArtifactRef. UNKNOWN и pending нельзя объявлять готовым результатом. Один клиентский wrapper этот пробел не закрывает.

## 13. Compute Export: владелец байтов, ключ и границы источника

Provisional `/v1/artifacts/exports` заменён существующим контрактом BeginUpload → presigned PUT → Seal. В совместном процессе Compute использует тот же Artifacts owner с проверенным task principal и свежей авторизацией, без второго store/SQL. Раздельный HTTP-режим использует публичный Go SDK: требуются явно настроенные HTTPS, CA и workload certificate, соответствующий текущему task token. Перенос task token под чужой workload не является делегированием и отвергается; отдельный delegated-workload протокол здесь не добавлялся.

Export требует стабильный `key`, `computer_id`, `path`. Сервер не генерирует ключ за клиента. Compute сначала фиксирует durable binding `(tenant,deployment,key)` к subject/computer/task/context/нормализованному пути/версии запроса. Смена target или task даёт KEY_REUSE_MISMATCH; другой subject получает FORBIDDEN без чужих metadata. Это identity binding, а не второй status/result ledger; SHA/size и результат публикации остаются у Artifacts. Binding сохраняется при обычном Destroy и удаляется только при subject/tenant erasure вместе с Computer. Повтор сверяет путь/байты и возвращает прежний sealed ID/version без нового PUT; потерянный ответ Seal разрешается через Get. Иное содержимое под тем же ключом получает owner `KEY_REUSE_MISMATCH`. Секреты не передаются в PUT и не возвращаются в ArtifactRef; отсутствующий у owner `sealed_at` опускается.

Источник ограничен смонтированным home конкретного Computer через os.Root; общий jail больше не является разрешением читать соседний Computer. В разрешённом PoC используется quiescent export: running incarnation, команда с незавершённым/UNKNOWN исходом, PTY или pending install запрещают экспорт. Scoped row guard и Redis writer удерживаются от решения о quiescence до owner Seal; lifecycle/command/PTY входы ждут PostgreSQL row/FK lock, patch — writer lock. Файл копируется из того же дескриптора в private временный snapshot с проверкой размера, metadata до/после и cancellation; последующая перезапись исходного inode не меняет snapshot. Ссылки наружу и archive links/special files запрещены. Предел: 64 MiB байтов, 10 000 элементов архива, 45 секунд операции; activity/writer leases и наличие guard перепроверяются перед owner-вызовами. Отзыв/expiry JWT и secret taint после PUT блокируют Seal; concurrent incarnation mutation ждёт завершения Seal. Guard использует максимум 2 отдельных соединения на процесс, Identity authority pool — максимум 2/минимум 0; основной Compute pool сохраняет настроенный предел. Cleanup закрывает authority pool при ошибке startup и отмене server context, guard — при любом завершении запроса. Точка публикации — успешный owner Seal; отзыв после этой точки запрещает дальнейшее чтение, но не является ретроактивным удалением.

Границы: host home принадлежит оператору; это не доказательство microVM isolation. Это bounded private copy quiescent источника, не snapshot гипервизора или активной VM. Для активных источников потребуется настоящий snapshot backend; выдача отложена до quiescence. Экспорт исчезнувшего ephemeral scratch не подменяется чужим каталогом: требуется существующий смонтированный per-Computer home. После потери ответа replay требует доступности того же источника для сверки; durable receipt находится у Artifacts owner. Совокупную память параллельных 64 MiB экспортов ещё нужно замерить нагрузочным тестом. Реальные Go/Python SDK и новая общая сборка проверяются отдельно от этого owner-блока.

Отдельный startup-дефект вне этого блока: State.Migrate держит session advisory lock на одном pool connection и запускает дочерние migrations через тот же pool; MaxConns=1 исчерпывает pool до deadline. В доказательстве Compute bootstrap migrations выполнены отдельным обычным pool, затем runtime проверен с MaxConns=1. Это не утверждение, что весь startup работает при pool1.

Совместимость старого `cmd/compute-host`: его GET скачивания теперь направляется в текущий Artifacts Download с исходными TLS/token/Range/context; экспорт использует BeginUpload/PUT/Seal и текущий task token. Сам этот бинарь всё ещё требует явный `AHP_COMPUTE_ALLOW_ALL_AUTHZ=1`, а его Workspace hooks являются development-only: smoke не подтверждает production IAM или отзыв гранта. Такие проверки выполняет `cmd/ahp/TestComputeExportRealOwners`. У старого lifecycle обнаружена отдельная граница: Sleep убивает host processes и меняет Computer.status, но оставляет control-incarnation от Wake running; перед quiescent Export требуется явный StopIncarnation этих записей через API. Guard не считает такую запись остановленной автоматически. Полное settlement Sleep и physical VM snapshot здесь не заявлены.

## 14. Шифрование at-rest и tenant-привязка ключа (профиль блока)

Требование: §8.3 (tenants … свои State Store, бакеты и ключи KMS) и §10 (Tier 0 — ключи KMS по tenant, Tier 1 — BYOK клиента, Tier 2A — PG/S3/KMS у клиента, Tier 2B — вся ячейка локально). PDF не выбирает реализацию и не называет вендорский KMS API; выбор реализации фиксируется здесь. Разрешённый синтетический внешний KMS/BYOK не отменяет шифрования и не превращает plaintext-хранение в доказательство at-rest: TLS-успех и «ключевой» HTTP-ответ КМС ничего не говорят о байтах на диске.

Блок поставляет `internal/atrest` — механизм envelope-шифрования на проверенных upstream-примитивах: AES-256-GCM (аутентифицированное шифрование) и HKDF-SHA256 (RFC 5869) из стандартной библиотеки Go 1.26. Самодельной криптографии нет. На каждую запись берётся случайный DEK из `crypto/rand`, им шифруется payload; DEK обёртывается KEK, выведенным HKDF из мастер-ключа tenant с привязкой (tenant, keyID, version). И tenant/version, и purpose входят в AAD обоих слоёв GCM, поэтому подмена tenant, ключа, версии или назначения ломает аутентификацию, а не даёт «тихий» plaintext.

Модель доверия: ключ — это операторский/tenant-авторитет, а не носитель задачи. Read-интерфейс `KeyManager` не имеет метода принять ключевой материал или выбрать чужой ключ; мутации (`Provision/Rotate/SetStatus`) живут на отдельном `KeyAuthority`, который обычным владельцам хранилищ не выдаётся. Аргумент tenant в `Seal/Open` обязан приходить из аутентифицированного серверного scope, а не из шифруемых данных. Профили: Tier 0 — операторские мастер-ключи по tenant (детерминированно выводятся из root-секрета оператора, поэтому переживают рестарт); Tier 1 — BYOK, мастер-ключ tenant задаётся материалом клиента и интероперирует между инстансами авторитета. `Seal` отказывает, если у tenant нет активного ключа (нет ключа по умолчанию); `Open` отказывает на disabled/revoked версии; ротация помечает предыдущую версию rotated и оставляет её читаемой.

Что доказано (реальные изолированные PG/MinIO/Redis lanes, без вывода plaintext/ключей): раундтрип seal/open; байты на хранении отличаются от plaintext и не содержат маркера plaintext; wrong-tenant → отказ изоляции; wrong-key/purpose/tamper → отказ аутентификации; ротация читает старые версии; disabled/revoked → отказ; повторный запуск/новое соединение с тем же профилем оператора читает ранее записанные строки; malformed → отказ до обращения к ключу. Это доказательство уровня «примитив + owner-байты в изолированном стенде», а не production/HA/внешний вендорский KMS.

Непокрыто этим профилем и заявлено явно: метаданные и индексы (см. §15) остаются plaintext; нативные векторы pgvector и tsvector-индекс утекают даже при шифровании текста; физическое шифрование дисков/тома и носителей бэкапов, резидентность Tier 2A/2B — отдельная средовая проверка, не доказанная библиотекой; реальный внешний KMS (Vault transit и т.п.) не подключён — механизм готов к бэкенду, но здесь это синтетический операторский авторитет.

## 15. Инвентарь границ персистентности и остаток plaintext

Владелец-оператор и состояние на revision 7a3a7a22 (проверено чтением DDL владельцев; это инвентарь, а не утверждение о полном покрытии). `internal/atrest` пока механизм: он ещё не внедрён в write-path владельцев, потому что мутации чужих схем требуют решения штаба. Ниже — что реально лежит открытым текстом.

- State (owner State API, PostgreSQL `ahp_state`): открытым текстом `runs.payload jsonb`, `checkpoints.metadata jsonb`, `checkpoint_blobs.data bytea`, `checkpoint_writes.data bytea`, `kv.value jsonb`, `kv_ops.result jsonb`, `inbox_events.payload jsonb`, `stream_events.payload jsonb`. Хэши `body_digest/digest` — не содержимое, но утечка метаданных. Кандидат на `Seal` с purpose вида `state.payload`/`state.blob`.
- Artifacts (owner Artifacts, MinIO + `ahp_artifacts`): байты объекта в MinIO — plaintext; метаданные `mime, sha256, size, labels, request_digest` — plaintext. Кандидат на `Seal` байтов object storage с purpose `artifact.bytes`; sha256/размер остаются (иначе ломается seal/дедупликация).
- Memory (owner Memory, PostgreSQL `ahp_memory` и нативный `ahp_longterm`): `memories.text` — plaintext; `search tsvector` (полнотекстовый индекс из текста) и `embedding vector(N)` (pgvector) — производные, утекают содержимое даже при шифровании `text`; `evidence/provenance/labels jsonb` — метаданные; нативные `ahp_longterm.memory_records.body jsonb` — plaintext. Продуктовую семантику поиска/извлечения менять нельзя: чтобы шифровать `text` и сохранить поиск, нужны слепые индексы/отдельный поиск; векторы требуют shemating/зашифрованных ANN — это отдельный контракт, здесь не делается.
- Workspace (owner Workspace, PostgreSQL `ahp_workspace`): байтов файлов в PG нет — `files/candidate_files` хранят `path, artifact_id, mode, digest`; содержимое живёт в Artifacts/MinIO и покрывается шифрованием байтов артефактов. Дерево/пути/дайджесты/labels остаются plaintext-метаданными.
- Tools (owner Tool Gateway): raw-байты результата инструмента в PG не сохраняются (`guardian_log` — журнал без raw MCP result, см. §12), поэтому at-rest для результата включится, когда результат начнут персистить; OAuth/MCP секреты уже делегированы во Vault KV v2 (`oauth_connections.secret_path`, `oauth_secrets.path`), в PG лежат только пути/хэши/ручки — шифрование at-rest здесь = секретность/HA самого Vault, а не этого блока.
- Runtime-секреты в KV-подобных хранилищах (Redis leases/queues, gateway): значения не шифруются этим блоком; Redis — lease/cache, а не primary. Byte-check зашифрованного значения в реальном Redis сделан как демонстрация, что даже dump/память Redis не содержит plaintext, но сам Redis не зашифрован.

Ровный остаток plaintext, который этот блок НЕ закрывает и требует отдельных решений: все `*_digest/sha/body_digest`, `labels/provenance/evidence`, пути и имена, tsvector/векторные индексы Memory, метаданные артефактов, пути Vault, содержимое нативного Hindsight `ahp_longterm`. Их покрытие меняет контракты смежных владельцев (поиск, seal, GC, гранты) и выносится в RFC, а не вносится молча.

## Registry supply chain и deploy admission (lane registry-kms, 2026-11-09)

Реализовано (internal/registry): криптографическая проверка CI supply-chain вместо прежней непустой строки `RuntimeBinding.Attestation`. Использованы только публичные форматные спецификации и стандартная библиотека Go 1.26 (никакой самодельной криптосхемы и никакого caller-boolean «доказательства»): конверт DSSE (Dead Simple Signing Envelope, secure-systems-lab go-securesystemslib, PAE = `DSSEv1 <len> <type> <len> <b64payload>`) c in-toto Statement v1; подпись ECDSA P-256/SHA-256 (ASN.1 DER) поверх PAE, проверяемая `crypto/ecdsa`; сертификат подписанта проверяется цепочкой X.509 к операторскому набору доверенных корней (`crypto/x509`), EKU code-signing, окно валидности. Идентичность издателя берётся из SPIFFE URI SAN листа (`spiffe://ahp/publisher/<id>`) и обязана совпасть с фактическим владельцем агента в реестре. Подпись/SBOM/verdict привязаны к фактическому неизменяемому OCI digest `@sha256`.

Механизм включения — оператор: `WithSupplyChain(roots)` из `NewTrustRootsFromPEM`. При наличии корней `AdmitImage` и `RegisterRuntime` верифицируют провенанс и пишут строку `ahp_registry.admissions`; гейт `Install`/`Promote` (`requireDeployAdmission`) требует действующую запись admissions, совпадение version digest, всё ещё пройденный eval verdict по digest версии, а для stage/prod — действующий пройденный security verdict («проверка ИБ»). Добавлены таблицы `ahp_registry.admissions` и `ahp_registry.security_verdicts`. Отсутствующие корни сохраняют прежнее поведение оператора (supply chain включается ровно тогда, когда оператор установил корни) — это операторское решение доверия, а не флаг запроса.

Границы доказательств (не заявляем лишнего):
- Синтетический PKI/TLS-контур. CA и издательские листья генерируются в тестах; операторские корни синтетические, это НЕ продуктовый PKI/CI и НЕ живой OCI-реестр. Это НЕcosign/Notary/Sigstore и не внешний облачный KMS — только stdlib-верификация публичных форматов.
- Проверка привязана к настоящему digest'у содержимого: тесты считают `sha256` от фактических байт OCI-подобного манифеста и подписывают именно его (content-addressing как в OCI). Пуш/пул живого OCI-реестра и реальный rollout/rollback контейнеров здесь НЕ выполняются: закрыта сторона реестра (admission API + персистентность на реальной PG: подпись/SBOM/digest/eval/security). Финальная выкладка требует kubernetes-expert и собственных ресурсов ahp-handbook (deploy controller на prod по c.41) — отдельное доказательство rollout/rollback. `Store.Rollback` переключает на предыдущий digest и сохраняет пины задач (доказано), но сам container rollout не производит.
- SBOM связан как content-addressed блоб (в тестах CycloneDX JSON): реестр проверяет наличие и совпадение хэша с подписанным digest, но не семантическую полноту SBOM (полная валидация CycloneDX/SPDX не требуется PDF и не выполнена).
- Security verdict («проверка ИБ») — реестровая запись, которую выдаёт отдельная служба ИБ; реестр обязывает наличие действующей записи, на которую ссылается подписанный провенанс. HTTP-выставление `RecordSecurityVerdict` смонтировано как строго human-only административный маршрут (`AttachSecurityAuthority`, отдельный guard `securityAuth`), а НЕ как обычный admin-роут: он отказывает и workload/task-токену структурно (проверка `Kind==Human` до авторизатора), и при отсутствии прикреплённого авторитета (fail-closed 403). Издатель артефакта не может выдать себе clearance. Это намеренно уже, чем `registry:admin`: у обычного админ-роута авторизатор `attachRegistryManagement` допускает task с capability, чего для security verdict быть не должно.
- Разветвление решения (PDF c.41 задаёт порядок конвейера, но не называет инструмент подписи и формат SBOM): выбраны DSSE/in-toto + X.509 на stdlib как реализация требования «SBOM и подпись», без расширения scope. ИБ размещена на stage (по строке конвейера): dev-admission требует подпись/SBOM/digest + eval, но не пройденный security verdict; stage/prod требуют его дополнительно.
- ARCH-03: invoke уже маршрутизирует по digest выбранного runtime (подтверждено `TestInvokeRoutesBySelectedRuntimeDigest` и существующим `TestRegistryInvokeFullPath`); заготовка h26 `regprobe` @758e7aef суперсидена и не переносилась.
- Монтаж в продуктовой сборке выполнен в этой lane (`cmd/ahp/mount_w2a.go` `tryMountRegistry`, хелперы `cmd/ahp/registry_supplychain.go`). Режим supply chain обязателен при включённом реестре и НЕ может быть молча выключен: `AHP_REGISTRY_SUPPLY_CHAIN=enforce` требует `AHP_REGISTRY_TRUST_ROOTS_PEM` (ПУТЬ к PEM-бандлу операторских CA-корней, не ключ и не секрет в git) → `NewTrustRootsFromPEM` → `WithSupplyChain`; `AHP_REGISTRY_SUPPLY_CHAIN=disabled` оставляет плоскость без admission и громко пишет `logger.Warn`; пустое/неизвестное значение валит старт. Плюс к реестровому handler прикрепляется human-only авторитет `RecordSecurityVerdict` (`registrySecurityAuthority`: живая браузерная сессия + право `registry:security-verdict`/`registry:admin` или роль admin/tenant-admin с разрешённого control-deployment). Тесты: `TestMountedCompositionRejectsUnsignedRuntime` (композиция `WithEvalGate`+`WithSupplyChain` отвергает неподписанный runtime), `TestRecordSecurityVerdictRouteIsHumanOnly` (task→403 без записи, human→200 с записью, без авторитета→403), `TestRegistrySupplyChainOptionFailClosed` (режим fail-closed).

- Внешний prerequisite (в этой lane НЕ выполняется и не заявляется): живой OCI-реестр (push/pull по digest), реальный container rollout/rollback на Kubernetes (deploy controller по c.41), внешний подписант cosign/Sigstore/Notary и внешний облачный KMS — это инфраструктура вне реестрового кода. Проверить наличие/живость внешнего OCI-реестра отдельно: `oras manifest fetch <registry>/ahp/agent@sha256:<digest>` (или `docker manifest inspect <ref>@sha256:<digest>`) должен вернуть манифест по тому же digest, что принял гейт admission.
## 16. Формат конверта: длина поля и потолок 64 KiB (суперсессия принятого снапшота)

При замере оверхеда (Seal на 1 MiB) обнаружен реальный дефект первой версии формата: префикс длины переменной части был 2-байтным, поэтому `Seal` отклонял любой ciphertext больше 64 KiB (ошибка ErrMalformed). Принятые 22 теста были на малых payload и дефект не проявляли. Исправлено: префиксы длины — 4 байта (uint32, потолок 4 GiB), плюс отказ читать объявленную длину больше фактических оставшихся байт (защита от giant-alloc на подделанной длине). Добавлен регресс-тест `TestLargePayloadRoundtrip` (~2.2 MiB). Постоянный оверхед конверта вырос с ~111 до ~123 байт + длины tenant/key id (пренебрежимо на MiB-объектах). Формат-версия оставлена 1: боевого шифртекста ни в одном хранилище нет (write-path владельцев ещё не подключён), поэтому обратной совместимости с 2-байтным снапшотом не требуется. Кто интегрировал прежний снапшот — берёт этот коммит как актуальный кандидат.
