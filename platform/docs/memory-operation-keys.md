# Ключи операций PDF Memory

Контракт канонического Store и `/v1/memory/shared/`. Native Hindsight API и его
личные/private-project банки не меняются.

| Запрос | Что делает |
|---|---|
| `Read {id}` | Читает память с текущими ACL и журналом меток |
| `Get {op_key}` | Возвращает квитанцию без текста памяти |
| `Fence {op_key}` | Закрывает ещё не зафиксированный ключ; не удаляет данные |
| `DeleteSubject {op_key, subject}` | Отдельное привилегированное удаление пользователя |

Пример квитанции: `{"op_key":"step-4-call-2","status":"SUCCEEDED","result_id":"...","result_count":0}`.
`result_id` исключается, если источник уже удалён, просрочен или доступ отозван.
Итог операции при этом остаётся SUCCEEDED: отзыв доступа не отменяет совершённую запись.
Digest, текст, evidence и provenance в квитанцию не копируются.

Ключ уникален в `(tenant, deployment)`, как требует PDF §6.3. Другой subject
не получает квитанцию и не может закрыть уже занятый ключ (404). Попытка мутации
с ключом другого subject или другим отпечатком получает KEY_REUSE_MISMATCH.
Другой deployment имеет независимое пространство ключей.

Memory применяет изменение и записывает SUCCEEDED в одной PostgreSQL-транзакции.
Резервация ACCEPTED не видна до её commit. У этого владельца нет отдельной
асинхронной отправки внешней мутации, поэтому DISPATCHED и SIDE_EFFECT_UNKNOWN
для этой локальной записи не имитируются. Rollback не оставляет успешную квитанцию.

Если Fence выиграл до резервации, сохраняется FENCED и будущая мутация получает
409 CONFLICT с `reason=FENCED`. Если реальная запись уже держит ключ, Fence ждёт
её commit/rollback; после commit возвращает SUCCEEDED и ничего не стирает.
Embedding-запрос, начавшийся до Fence, может завершиться; запись памяти после
победившего Fence не допускается. Это не отмена вычисления модели на её стороне.

После потерянного ACK SDK не повторяет мутацию автоматически. Клиент обращается
к Get/Fence с прежним ключом или явно повторяет прежние аргументы и ключ.
404 от Get не доказывает, что параллельный запрос уже закончил работу: его
транзакция могла ещё не зафиксироваться. Новый ключ не используется для обхода
такой неопределённости. Квитанции/закрытые ключи сейчас хранятся без автоматического
истечения; окно хранения не сокращается.

При обновлении старой схемы сначала восстанавливается журнал по старому ключу,
затем включается уникальность deployment. Исторические коллизии разных subjects
останавливают миграцию без выбора победителя и без удаления записей. Для таких
данных оператору нужен отдельный план разрешения коллизий; автоматическая
смена старых ключей была бы нарушением идемпотентности.

Проверки: `internal/memory/memoryapi/operation_pg_test.go`,
`internal/memory/operation_fence_pg_test.go`, контракт Go/Python SDK и
`TestSharedMemoryKeyFenceOnDeployedOwner` на фактически запущенном сервере.
Наличие кода теста само по себе не означает приёмку: конкретные сборки и результаты
зафиксированы внешними неизменяемыми receipts стенда.
